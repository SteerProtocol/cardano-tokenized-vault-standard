# CTVS-2 semantic conformance comparison

Reviewed 18 September 2026 against the supplied illustrated revision 0.6.3, semantic revision 0.6, WIRE-2/profile 0. Page numbers below are the physical pages of the combined 85-page PDF.

## Scope and method

This report covers CTVS-2 sections 1 through 11 and 13 through 16, plus the revision boundary and acceptance checklist, on combined PDF pages 45 through 85. Detailed constructor/wire rules in section 12.1 through 12.5 belong to the wire review. The required common response, authenticated lineage and rollback interface in sections 12.6 and 12.7 belongs to the integration review; its acceptance consequences are still recorded here in A-13/A-15.

The comparison reads every applicable page, the actual async Aiken entrypoints and shared predicates, both public client planning paths, retained Aiken and TypeScript tests, signed integration fixtures and validation artifacts. It decomposes the paper into individual obligations instead of treating an entire section or a passing test count as conformance. The machine-readable ledger is [ctvs2.requirements.json](ctvs2.requirements.json). Code and test locations are repository-relative and one-based.

`aligned` means the inspected implementation expresses the stated obligation at the cited evidence level. It does not mean universal correctness, ledger certification, measured safety coverage or independent audit. `retained_test` means an existing test was inspected; this reviewer did not rerun the full suite. Root owns the fresh full-suite result. `executed_probe` is limited to the named review experiment. Missing branch-specific tests are named in each closure field even when the source aligns.

This reviewer made no production changes and did not mutate shared compiler staging. The only new executable artifacts are isolated, read-only SDK/arithmetic probes. Root separately supplied a signed resource sweep.

## Actual differences

1. **Authorized-key hex spelling can change SDK authorization.** `C2-006` is a reproducible SDK contradiction: credential serialization gives identical bytes for lower/uppercase spelling, but `buildBatchPlan` uses case-sensitive string membership. The uppercase spelling is rejected as unauthorized although the onchain predicate compares byte arrays. This is a false rejection, not a custody bypass. [Code](../../../reference/implementations/ctvs2/client/src/batch.ts#L54), [probe](probes/c2-client-boundaries.ts#L16), [result](probes/c2-client-boundaries.result.json).
2. **One async family cannot express mixed direct/async modes.** `C2-002` is an intentional implementation subset: mode masks are only 4, 8 or 12. It cannot implement direct entry plus async exit on the same vault, despite the shared wire allowing all masks 1 through 15. The family label and conformance claim must make this explicit. [Code](../../../reference/implementations/ctvs2/onchain/lib/ctvs2/state.ak#L9).
3. **The delivery SDK accepts a smaller source-address domain than Q.** `C2-064`: Q recognizes its payment script regardless of source staking credential. The client requires enterprise Q. An executed probe confirms the client false rejection; Q acceptance was inspected in source, not compiled in this review. Authentic Batch claims are enterprise outputs, so ordinary generated claims are unaffected. [Q](../../../reference/implementations/ctvs2/onchain/lib/ctvs2/claim.ak#L35), [SDK](../../../reference/packages/planning/src/context.ts#L63).
4. **Refund and delivery top-ups require a manual plan change.** `C2-065`: the guards permit output value at least the entire input value, including externally funded additions. Public planner options expose no receiver top-up and emit exact input value. This matters when a changed minimum-ADA requirement needs explicit extra funding; the test adapter intentionally rejects silent builder changes. This is a client construction limitation, not a restriction in the contracts. [Refund](../../../reference/implementations/ctvs2/client/src/recovery.ts#L13), [delivery](../../../reference/implementations/ctvs2/client/src/delivery.ts#L11).
5. **Structural batch size 16 is not a working capacity claim.** `C2-088` and `C2-104`: new root-executed signed deposit-only probes passed sizes 1, 2, 4, 5, 6 and 7 for each of four shapes, then failed at 8 on memory. Native backing with a script receiver carrying a 512-byte payload used 13,898,477 memory at 7. The unchanged local ceiling is 14,000,000. The paper already says its cap is structural, so this is an exposed feasibility limit, not a contradiction in its promised throughput. Separate signed delivery probes accepted 1, 4 and 5 Claims for native-share Claims to key or script512 recipients; 6 through 8 failed memory. Size 16 failed builder size before signed evaluation: 18,324 bytes for key recipients and 26,964 for script512, with Q attached by the adapter. [Batch probe](probes/integration-probes.ts#L20), [batch evidence](evidence/integration-probes.json), [delivery probe](probes/delivery-capacity.ts#L15), [delivery evidence](evidence/delivery-capacity.json).

No confirmed onchain accounting or payout contradiction was found in this bounded source-and-test comparison. That statement does not close untested inputs or the paper's acceptance gates.

## Core semantics checked

- Request creation leaves backing and supply alone, distinguishes candidate origination from authority, and learns its ID only after construction.
- Settlement checks actual State/Config identity, recomputes each full-fill quote against one old State, rounds fees per request, preserves gross supply obligations even at zero net mint, and checks every Request in the actual consumed P domain.
- Actual value, Terms, mode, expiry, positive result, user minimum, successor state and all Claim/reward output allocations are checked together. Distinct obligations cannot reuse the same output index.
- Refund dispatch reads Recovery before economic downcast. Unsupported economics and surplus assets do not disable valid fixed recovery. State/ID custody cannot select Request recovery.
- The interval is finite, nonempty, lower-inclusive and upper-exclusive. Settlement allows upper equal to deadline; expiry requires lower at or after deadline; controller cancellation remains available later.
- Q requires one common exhaustive semantic list across all consumed Q Claims, distinct outputs, exact destinations and preservation of every actual input asset. It does not read mutable vault state, reprice or mint.
- Pause bits act on their economic direction. The SDK probe exercised all eight direction/pause combinations and creation remained available. Contract source matches, but the full compiled pause matrix is not retained.

The [semantic example probe](probes/c2-semantic-examples.ts) reproduces the exact three-request paper example and the two order-dependent histories. It does not prove the supplied initial states reachable from this async-only family or make a signed ledger transaction.

## Important acceptance gaps

The requirement ledger distinguishes an implemented check from its evidence. Missing or partial evidence includes a signed mixed zero-net batch, a signed cancel-versus-settle race, node-backed slot boundary behavior, all directional pause combinations at compiled level, signed third-party fixed delivery with original roles absent, independent wrong-asset/quantity/reserve mutation tests, multi-request non-dilution properties, and complete model-to-validator refinement.

The new resource sample is deliberately restricted: deposit requests, selected integer sizes, one signer shape, key or 512-byte script-datum receiver, and local parameters. It is not a proof for all allowed 16-entry batches, maximum recipient data, mixed/redemption batches or target-node parameters. The delivery sweep adds signed final outputs to script512 receivers but still does not cover maximum recipient data or every witness shape. Seven for settlement and five for delivery are not new normative or universally safe caps.

Production lifecycle response/indexing, rollback/replay, independent construction/indexing and original source-bundle reconciliation remain missing. Those are required infrastructure or acceptance work, not optional native extensions. Direct-at-settlement, managed NAV, script controllers, inventory, partial fills, epochs, transferable claims and generalized routing are explicitly separate or deferred in the paper and are correctly excluded from profile 0.
