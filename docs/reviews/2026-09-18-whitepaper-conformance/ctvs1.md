# CTVS-1 economics and direct-execution conformance review

Reviewed source commit: `75d47c90361d6f83458841b871e0f746500610e0`. Date: 18 September 2026. Source paper: `CTVS-Whitepapers-v0.6.3-Illustrated-Combined.pdf`, PDF pages 1-28 and 35-36, with sections 1-3, 5-9 and 12 (PDF pages 35-36) reviewed in full and section 4 succession/terminal rules consulted. Detailed genesis, build binding and wire decoding belong to the separate identity/wire review.

The machine-readable companion is [ctvs1.requirements.json](ctvs1.requirements.json). Each row is a paraphrased requirement with applicability, source/test pointers, evidence level, impact and a closure action. `aligned` means no mismatch was found at the recorded evidence boundary. It does not mean formal proof, full ledger acceptance, independent external authorship or production readiness.

## Result

No contradictory direct accounting equation or demonstrated direct-contract value loss was found in this pass. The real differences are narrower deployment capabilities and incomplete offchain semantics: standalone quote provenance, zero-supply display status, and economic-minimum/status reporting. The manifest also separates source alignment from external ledger and script-user acceptance gates.

Entry-only and exit-only modes are still allowed by both the current paper and current family predicates. The proposal in `LIMITATIONS.MD` has not changed implementation behavior and is not counted as a paper/code mismatch. Native mappings, inventory supply and managed NAV are outside this profile and are not marked as missing direct-contract features.

### Fresh review probes

- [Independent integer oracle](probes/c1-economics.ts) transcribed the paper equations using a quotient/remainder ceiling implementation and compared production TypeScript outputs and acceptance boundaries. Expected transitions did not call production transition helpers. [Recorded output](probes/c1-economics.result.json): 183,678 quote comparisons, 367,356 transition comparisons, 2,352 conversion-invariance comparisons, 4,032 independently enumerated maximum-deposit markets, and 2,560 upper-domain comparisons. The updated probe also checked adjusted-price monotonicity on 94,204 accepted transitions and immediate deposit/redeem bounds on 39,954 cases. These categories overlap and must not be added into a safety-coverage percentage. No counterexample was found in this bounded corpus.
- [Compiled predicate probes](probes/c1-onchain.ak) ran 16 new focused Aiken cases in an isolated temporary project, leaving authored source and shared `.build` untouched. [Recorded output](probes/c1-onchain.result.json): 16 passed, 0 failed. They cover exact-output maxima, independent pause directions, disabled pause authority, zero-liability collection, permissionless collection while fully paused, native fee under/overpayment, zero/incorrect top-up, protected output shape, and non-authoritative extra references.
- The Aiken positive fixtures balance visible value. Mutated negative fixtures establish the selected source predicate rejection; they are not all separately rebalanced signed ledger transactions. These probes use fixture identities and call compiled source predicates, so they do not establish real genesis history, actual key signatures or node phase-1 behavior.
- Existing tests cited below were inspected, not individually rerun by this reviewer. The coordinating review runs the baseline suite separately. Existing test names are not treated as proof of every behavior implied by their name: for example, `rejects_receiver_datum_hash_or_inline_mismatch` actually mutates an inline datum, so a dedicated datum-hash compiled negative remains useful.

## Interpretation of open items

1. **Capability narrowing:** supporting only pure synchronous and pure asynchronous families is a supported subset of the paper, not implementation of every permitted hybrid configuration. Code and manifests are explicit about the subset.
2. **Quote provenance:** `preview()` is a correct arithmetic primitive for its supplied objects. The gap appears when its result is treated as the paper's standalone quote response: no consumed State OutRef or authenticated chain-point evidence accompanies it. The eventual direct plan does identify the State input.
3. **Views and limits:** `maxDeposit()` correctly avoids the non-prefix-validity search trap and labels construction limits unknown. Missing economic-minimum/bootstrap-residual reporting is an interface gap. The paper does not prescribe a complete ERC-style ABI or license inventing maximum formulas for other actions.
4. **External acceptance:** native script-controlled users and full node-backed ledger validation are separately declared requirements. Their absence does not invalidate the direct arithmetic checks, and source alignment does not close them.
5. **Wallet effects are a different boundary:** exact protected State/receiver outputs establish vault obligations. They do not alone establish that all additional wallet funding, change, network fees and collateral effects were intended by the user. See the integration reviewer's independent pre-signing probe for that separate common requirement.
